Frontend Stack Decision
React vs Vue vs TypeScript vs CSS Frameworks — kapan dan kenapa

React vs Vue: Framework Pilihan

◆ Pilih jika...
React
Tim besar, ekosistem NPM kompleks, butuh fleksibilitas tinggi, integrasi dengan library lain (tabel, chart, dll), long-term project dengan banyak developer. Meta maintain aktif, hiring lebih mudah.
◆ Pilih jika...
Vue 3
Tim kecil–menengah, developer dari background Laravel/PHP, butuh produktivitas cepat, Inertia.js, atau project yang tidak butuh ekosistem NPM besar. Learning curve jauh lebih landai.
React — Kelebihan
  • Ekosistem terbesar di dunia
  • Fleksibel, tidak opinionated
  • Server Components (Next.js)
  • Hiring pool besar
  • Mature tooling (Vite, CRA)
React — Kelemahan
  • JSX learning curve
  • State management kompleks
  • Banyak keputusan arsitektur
  • Bundle size lebih besar
Vue — Kelebihan
  • Template syntax intuitif
  • Composition API modern
  • Dokumentasi luar biasa
  • Opinionated = konsisten
  • Cocok dengan Laravel
Vue — Kelemahan
  • Ekosistem lebih kecil
  • Lebih sedikit job market
  • Nuxt.js lebih muda dari Next.js

TypeScript: Kapan Wajib?

⚡ Keputusan Praktis

Gunakan TypeScript SELALU jika: project > 3 bulan, tim > 2 orang, ada shared types antara FE–BE (API contracts), atau project akan di-maintain jangka panjang.

Boleh skip TypeScript jika: prototype/MVP cepat (< 2 minggu), solo project yang tidak akan di-scale, atau tim tidak familiar dan deadline ketat. Tapi tetap tambahkan di iterasi berikutnya.

Real-world fact: Kebanyakan bug production di JS berasal dari type mismatch. TypeScript mengeliminasi ~80% dari ini di compile time.

CSS Framework: Tailwind vs Bootstrap vs Lainnya

◆ Industri Modern
Tailwind CSS
Utility-first. Tidak ada CSS conflicts. Bundle size kecil (purge). Custom design system yang konsisten. Recommended untuk project baru. Semua komponen dibuild dari utility class, sangat fleksibel.
◆ Legacy / Cepat
Bootstrap 5
Cocok jika butuh prototype sangat cepat, tim sudah familiar, atau project internal yang tidak butuh custom design. Jangan pakai untuk SaaS product dengan UI custom — hasilnya terlihat generik.
◆ Component-first
shadcn/ui + Radix
Copy-paste components ke project sendiri. Tidak ada vendor lock-in. Aksesibel by default. Cocok untuk SaaS, dashboard, admin panel modern. Pair dengan Tailwind.
⚠

Jangan campur framework CSS! Menggunakan Tailwind + Bootstrap bersamaan = konflik specificity, bundle besar, dan inconsistent styling. Pilih satu, commit penuh.

Arsitektur Backend
Controller vs Service vs Repository, Monolith vs Microservices

Controller vs Service Layer vs Repository Pattern

Ini adalah salah satu keputusan paling krusial. Kesalahan di sini akan terasa 6 bulan ke depan saat codebase mulai tumbuh.

PolaKapan DigunakanTrade-off
Fat Controller MVP, prototype, project < 3 bulan, solo developer Cepat develop, tapi tidak scalable. Sulit di-test.
Controller + Service Project menengah, butuh reuse logic antar controller, tim > 2 orang Balance antara simplicity dan maintainability. Default pilihan untuk 80% project.
Controller + Service + Repository Butuh swap database, unit testing yang strict, domain logic kompleks Paling maintainable tapi overhead tinggi. Jangan gunakan prematur.
⚡ Aturan Praktis

Mulai dengan Controller + Service. Controller hanya bertugas: validasi request, panggil service, return response. Tidak ada logika bisnis di controller.

Tambah Repository hanya jika: kamu butuh unit test yang mock database, atau punya plan untuk ganti ORM/database di masa depan. Untuk 90% CRUD apps, Repository adalah over-engineering.

Contoh struktur yang benar
// ❌ Fat Controller — JANGAN
class OrderController {
  public function store(Request $request) {
    // validasi, kalkulasi harga, kirim email, update stok — semua di sini
  }
}

// ✅ Controller + Service — BENAR
class OrderController {
  public function store(OrderRequest $request) {
    $order = $this->orderService->createOrder($request->validated());
    return OrderResource::make($order);
  }
}

class OrderService {
  public function createOrder(array $data): Order {
    // business logic di sini
  }
}

Monolith vs Modular Monolith vs Microservices

◆ Default Pilihan
Monolith
Untuk 90% project. Lebih mudah di-develop, deploy, debug. Tidak ada network latency antar service. Cocok sampai tim 10–15 orang atau 100k+ user/bulan.
◆ Skalabilitas Terstruktur
Modular Monolith
Monolith tapi terorganisir dalam module (Billing, User, Inventory). Deployment tetap satu unit. Persiapan jika suatu saat perlu pisah ke microservice. Ideal untuk team menengah.
◆ Hanya jika terpaksa
Microservices
Hanya untuk: team besar (50+ developer), deployment independent antar domain, scaling berbeda per service. Overhead operasional SANGAT tinggi: service discovery, distributed tracing, eventual consistency.
⚠

Real-world warning: Amazon, Netflix mulai dengan monolith. Mereka pindah ke microservices saat memang sudah butuh, bukan dari awal. Kebanyakan startup yang langsung microservices gagal karena complexity overhead mengalahkan business value.

Auth & Authorization
Session vs Token, Breeze vs Jetstream, RBAC vs Permissions

Session vs Token-based Auth

◆ Web App Standard
Session-based (Sanctum SPA)
Cookie + CSRF protection. Otomatis di browser. Lebih aman dari XSS karena token tidak disimpan di localStorage. Pilihan default untuk SPA yang hosted di domain yang sama.
◆ API / Mobile
Token-based (Sanctum Token / JWT)
Untuk API yang dikonsumsi mobile app atau third-party. Stateless. Token disimpan di client — wajib secure storage (tidak localStorage!). Sanctum token lebih sederhana dari JWT untuk Laravel.
⚡ Kapan Pilih Apa

SPA (React/Vue) + Laravel di domain sama: Gunakan Sanctum SPA mode (cookie-based). Lebih aman, tidak ada token di JS.

Mobile app (React Native, Flutter): Gunakan Sanctum API Token atau JWT. Token disimpan di Secure Storage, bukan di memory/localStorage.

API publik/third-party: JWT lebih cocok karena stateless dan bisa di-verify tanpa DB query.

Breeze vs Jetstream vs Custom

PilihanGunakan JikaJangan Jika
Laravel Breeze Butuh auth standar cepat, project sederhana, suka kontrol kode sendiri Butuh fitur 2FA, team management out-of-box
Laravel Jetstream Butuh 2FA, API tokens, team management, profile photo. Cocok untuk SaaS. Project sederhana — Jetstream opinionated dan sulit di-customize
Custom Auth Auth flow yang sangat spesifik (SSO, OAuth custom, multi-tenant) Hampir semua kasus umum — jangan reinvent the wheel

RBAC vs Simple Role vs Spatie Permission

◆ Project Kecil
Simple Role (enum)
User punya column role berisi admin/editor/user. Cukup untuk 3–5 role statis. Tidak perlu library tambahan.
◆ Standar Industri
Spatie Laravel Permission
Role + Permission yang bisa di-assign dinamis. Permission bisa di-cache. Mendukung multi-guard. Gunakan ini untuk hampir semua project menengah ke atas.

Brute Force Protection

// Laravel built-in rate limiting di RouteServiceProvider atau route
Route::middleware('throttle:5,1')->post('/login', [AuthController::class, 'login']);
// 5 requests per 1 menit

// Atau gunakan RateLimiter facade untuk custom logic
RateLimiter::for('login', function (Request $request) {
    return Limit::perMinute(5)->by($request->email . $request->ip());
});
⚠

Jangan simpan token JWT di localStorage! Rentan XSS. Gunakan httpOnly Cookie untuk web, atau Secure Storage untuk mobile. Ini adalah mistake paling umum di implementasi JWT.

Database Design & ORM
MySQL vs PostgreSQL, Eloquent vs Query Builder, Indexing

MySQL vs PostgreSQL

◆ Familiar & Luas
MySQL 8+
Lebih familiar di komunitas Laravel. Hosting support lebih luas. Performa baik untuk read-heavy apps. Default di banyak shared hosting.
◆ Lebih Powerful
PostgreSQL
JSONB lebih cepat dari MySQL JSON. Full-text search lebih baik. Strict SQL compliance. Window functions, CTE lebih mature. Pilihan terbaik untuk project baru di VPS/cloud.
⚡ Keputusan Praktis

Gunakan PostgreSQL jika di-host di VPS, cloud (AWS RDS, Supabase, Railway, Render), atau project yang butuh query kompleks.

Gunakan MySQL jika shared hosting yang hanya support MySQL, atau tim sudah familiar dan tidak ada kebutuhan fitur PostgreSQL-spesifik.

Normalisasi vs Denormalisasi

StrategiKapanContoh
Normalisasi penuh (3NF) Default untuk semua table. Data konsisten, tidak ada duplikasi. Order → OrderItems → Products
Denormalisasi selektif Kolom yang sering di-aggregate/join tapi jarang berubah. Setelah profiling menunjukkan query lambat. Simpan total_price di orders daripada selalu SUM()
JSON column Data semi-structured yang tidak perlu di-query per field. Settings, metadata. user.preferences sebagai JSON

Indexing — Aturan Praktis

// Wajib index:
// 1. Foreign keys
// 2. Kolom yang sering di WHERE
// 3. Kolom yang sering di ORDER BY
// 4. Kolom yang sering di JOIN

// Laravel migration:
Schema::table('orders', function (Blueprint $table) {
    $table->index('user_id');           // foreign key
    $table->index('status');            // sering di WHERE
    $table->index(['user_id', 'status']); // composite — urutan penting!
    $table->index('created_at');        // sering di ORDER BY
});

// JANGAN index:
// - Kolom dengan cardinality rendah (boolean, status dengan 2-3 nilai)
// - Setiap kolom tanpa alasan — index memperlambat INSERT/UPDATE

Eloquent vs Query Builder vs Raw SQL

MethodGunakan UntukPerforma
Eloquent CRUD standar, relationship loading, 90% kebutuhan umum Overhead sedikit, acceptable untuk CRUD
Query Builder Query kompleks dengan banyak kondisi dinamis, reporting, aggregate Lebih cepat dari Eloquent, aman dari SQL injection
Raw SQL Query yang sangat spesifik, CTE, window functions, optimasi ekstrem Tercepat, tapi harus manual binding parameter
⚠

N+1 Problem adalah penyebab terbesar performa lambat. Selalu gunakan with() untuk eager loading relationship. Gunakan Laravel Debugbar atau Telescope untuk deteksi di development.

// ❌ N+1 Problem — 101 queries untuk 100 orders
$orders = Order::all();
foreach ($orders as $order) {
    echo $order->user->name; // query per item!
}

// ✅ Eager Loading — 2 queries
$orders = Order::with('user')->get();

Performa & Optimasi
Caching, Queue, Lazy vs Eager Loading — kapan perlu dan kapan over-engineering

Caching Strategy

Jenis CacheKapanTTL Typical
Query Cache Data yang jarang berubah tapi sering di-query (kategori, config, settings) 5–60 menit
Response Cache Endpoint publik yang hasilnya sama untuk semua user (landing page, product list) 1–30 menit
Redis Session Session store untuk horizontal scaling (multi-server) Per session lifetime
Object Cache Hasil komputasi berat (laporan, agregasi data besar) 1 jam – 24 jam
⚡ Aturan Cache

Jangan cache dulu sebelum ada masalah. Profile dulu dengan Laravel Telescope atau query log. Cache adalah solusi terakhir setelah query optimization.

Cache invalidation adalah masalah terbesar. Gunakan cache tags agar bisa invalidate secara selektif. Selalu pikirkan: "Kapan cache ini harus di-clear?"

// Cache dengan tags — mudah di-invalidate
Cache::tags(['products', 'category-5'])->remember('products-cat-5', 3600, function () {
    return Product::where('category_id', 5)->get();
});

// Saat product category 5 diupdate:
Cache::tags(['category-5'])->flush();

Queue & Background Jobs

Queue adalah salah satu tools paling underutilized di Laravel. Gunakan untuk semua operasi yang tidak perlu jawaban instan ke user.

◆ Jangan di request cycle
Tanpa Queue
Kirim email, generate PDF, proses gambar, panggil API eksternal — semua dilakukan synchronous. User menunggu 5-10 detik. Response time buruk.
◆ Standar Production
Dengan Queue
Push job ke queue, response balik ke user dalam <100ms. Worker di background proses task. User tidak menunggu. Retry otomatis jika gagal.
// Dispatch job ke queue
SendWelcomeEmail::dispatch($user)->onQueue('emails');
GenerateInvoicePDF::dispatch($order)->onQueue('documents');
ProcessUploadedImage::dispatch($file)->onQueue('media');

// Queue driver recommendation:
// Development: database (mudah debug)
// Production: Redis (performa tinggi)
// Alternative: AWS SQS (managed, reliable)

Kapan Optimasi vs Over-engineering

SituasiTindakan
Response time < 200msTidak perlu optimasi. Focus ke fitur.
Response time 200ms–1sProfile dulu, optimize query atau tambah index.
Response time > 1sInvestigasi wajib: cek N+1, missing index, atau heavy computation.
Query yang sama dipanggil >100x/menitKandidat untuk caching.
Task yang butuh >1 detikPindah ke queue.

Keamanan Web
XSS, CSRF, SQL Injection, API Security — wajib tahu

Perlindungan Wajib & Built-in Laravel

AncamanLaravel Built-inApa yang Harus Kamu Lakukan
SQL Injection Eloquent & Query Builder sudah prepared statements Jangan pernah raw SQL tanpa binding parameter. Jangan interpolasi string ke query.
CSRF VerifyCsrfToken middleware aktif default Pastikan semua form ada @csrf. API murni gunakan Sanctum SPA auth.
XSS Blade auto-escape: {{ $var }} Jangan gunakan {!! !!} kecuali untuk HTML yang sudah di-sanitize dengan strip_tags() atau HTMLPurifier.
Mass Assignment Eloquent $fillable atau $guarded Selalu define $fillable. Jangan gunakan $guarded = [] di production.

File Upload Security

// ✅ Validasi yang benar
$request->validate([
    'avatar' => 'required|file|mimes:jpg,jpeg,png|max:2048',
]);

// ✅ Generate nama file random — jangan pakai nama asli user
$filename = Str::random(40) . '.' . $file->getClientOriginalExtension();

// ✅ Simpan di storage/app/private — tidak accessible langsung via URL
$path = $file->storeAs('uploads', $filename, 'private');

// ✅ Stream file via controller untuk access control
public function download($id) {
    $file = File::findOrFail($id);
    abort_unless(auth()->user()->can('view', $file), 403);
    return Storage::disk('private')->download($file->path);
}
⚠

Jangan simpan file executable (PHP, JS) di folder public. Jangan percaya extension dari user. Gunakan finfo_file() atau getimagesize() untuk verify MIME type dari konten file, bukan nama file.

API Security Checklist

◆ Wajib
Autentikasi & Rate Limiting
Semua endpoint yang butuh data user harus authenticated. Rate limiting di semua public endpoint. Throttle login lebih ketat (5/menit per IP+email).
◆ Wajib
HTTPS & Headers
Selalu HTTPS di production. Set security headers: X-Content-Type-Options, X-Frame-Options, Strict-Transport-Security. Gunakan package spatie/laravel-csp untuk CSP.

Frontend Architecture
SPA vs MPA vs Hybrid, Inertia vs Livewire, State Management

SPA vs MPA vs Hybrid (Inertia / Livewire)

◆ Traditional
MPA (Blade + HTMX)
Setiap page full reload. SEO sempurna by default. Cocok untuk content site, blog, e-commerce sederhana. Tidak butuh JS framework. HTMX bisa tambahkan interaktivitas tanpa SPA complexity.
◆ Laravel + Modern UI
Inertia.js (Hybrid)
SPA experience tanpa REST API. Server routing tetap di Laravel. Component di React/Vue. Tidak perlu token auth terpisah. Best of both worlds untuk Laravel project dengan React/Vue.
◆ Server-driven UI
Livewire
Full-stack component di PHP. UI reaktif tanpa menulis JS. Cocok untuk form kompleks, data table, real-time update ringan. Kurva belajar rendah untuk developer Laravel.
◆ Jika butuh full decoupled
SPA + REST API
Frontend sepenuhnya terpisah dari backend. Butuh API design yang matang, CORS, token auth. Overhead tinggi tapi cocok jika ada mobile app atau third-party yang pakai API yang sama.

State Management

KebutuhanSolusiKapan
State per component React: useState / Vue: ref() Default. 80% kasus cukup local state.
State shared beberapa component React: Context API / Vue: provide/inject Data yang perlu di-share antar sibling tanpa prop drilling dalam.
Global state kompleks React: Zustand / Vue: Pinia Cart, auth state, notification, data yang perlu diakses dari mana saja.
Server state (API data) TanStack Query (React Query) Data dari API — caching, refetching, loading state sudah dihandle otomatis.
⚡ SEO Consideration

SPA murni = SEO buruk secara default. Jika butuh SEO (public content, marketing, e-commerce), gunakan SSR (Next.js, Nuxt) atau Inertia dengan SSR mode.

Inertia.js + SSR adalah sweet spot untuk Laravel project yang butuh SEO + modern UI.

Backend–Frontend Integration
REST vs GraphQL, API Resource, Error Handling Konsisten

REST vs GraphQL

⚡ Keputusan Langsung

Gunakan REST untuk 95% project Laravel. REST lebih mudah di-implement, di-cache (HTTP caching), dan familiar dengan semua developer.

Pertimbangkan GraphQL hanya jika: frontend sangat bervariasi (mobile + web + TV yang butuh data berbeda), data model sangat kompleks dengan banyak nested relationship, atau kamu punya dedicated GraphQL expertise di tim.

Jangan pilih GraphQL karena "modern". Complexity overhead GraphQL (schema, resolver, N+1 DataLoader, authorization per field) tidak sebanding untuk kebanyakan project.

API Resource & Response Structure

// Gunakan API Resource untuk semua response
// Jangan expose Eloquent model langsung!

class UserResource extends JsonResource {
    public function toArray($request): array {
        return [
            'id'         => $this->id,
            'name'       => $this->name,
            'email'      => $this->email,
            'created_at' => $this->created_at->toISOString(),
            // Sengaja tidak include 'password', 'remember_token'
        ];
    }
}

// Standar response structure — KONSISTEN di seluruh API
{

  "message": "...",        // opsional
  "meta": {                // untuk pagination

    "total": 100
  }
}

// Error response
{
  "success": false,
  "message": "Validation failed",

Error Handling Global

// app/Exceptions/Handler.php — centralized error handling
public function register(): void {
    $this->renderable(function (ModelNotFoundException $e) {
        return response()->json(['success' => false, 'message' => 'Data tidak ditemukan'], 404);
    });

    $this->renderable(function (AuthorizationException $e) {
        return response()->json(['success' => false, 'message' => 'Tidak punya akses'], 403);
    });

    $this->renderable(function (ValidationException $e) {
        return response()->json([
            'success' => false,
            'message' => 'Validasi gagal',
            'errors'  => $e->errors()
        ], 422);
    });
}

// .env untuk ganti driver:

// Temporary signed URL untuk private file

Clean Code & Maintainability
Kapan refactor, code smell, tanda arsitektur rusak

Prinsip yang Paling Penting di Laravel

◆ High Value
Single Responsibility
Controller hanya handle HTTP. Service hanya business logic. Model hanya data representation. Ketika class punya banyak alasan untuk berubah, pecah.
◆ High Value
Don't Repeat Yourself
Logic yang sama di 2+ tempat = kandidat untuk extract ke Service/Helper/Trait. Tapi jangan abstract prematur — duplikasi 1-2x masih acceptable daripada abstraksi yang salah.
◆ Medium Value
Explicit over Clever
Kode yang mudah dibaca > kode yang "clever". One-liner yang sulit dipahami lebih berbahaya dari 5 baris yang jelas. Kamu akan lupa "clever code" dalam 3 bulan.

Code Smells yang Harus Dihindari

Code SmellTandanyaSolusi
Fat Controller Controller > 100 baris, ada business logic, kalkulasi, email logic Extract ke Service class
God Model Model dengan 50+ method, berisi logic dari banyak domain Extract logic ke Service, gunakan Trait untuk grouping
Magic Numbers/Strings if ($status == 3), if ($role == 'admin') Gunakan PHP Enum atau Constants
Deep Nesting if/else/foreach yang nested 4+ level Early return, extract ke method, guard clauses
Long Parameter List Method dengan 5+ parameter Gunakan Data Transfer Object (DTO) atau array

Kapan Harus Refactor?

⚡ Rule of Three

Pertama kali: Just do it (quick implementation OK).

Kedua kali: Duplikasi terasa, tapi masih acceptable.

Ketiga kali: REFACTOR. Ini adalah sinyal bahwa abstraksi dibutuhkan.

Jangan refactor "preventive" sebelum kamu tahu pattern yang muncul. Abstraksi yang salah lebih buruk dari duplikasi.

Tanda Arsitektur Mulai Rusak

⚠ Red Flag
Perubahan kecil = banyak file berubah
Ganti format tanggal = edit 15 file. Ini tanda tight coupling. Solution: centralize logic, gunakan abstraksi yang tepat.
⚠ Red Flag
Takut touch code lama
"Jangan diubah, nanti rusak yang lain." Tanda tidak ada test coverage dan coupling tinggi. Prioritas: tambah test, lalu refactor.
⚠ Red Flag
Onboarding developer baru lambat
Developer baru butuh >1 minggu untuk kontribusi pertama. Tanda struktur tidak intuitif atau tidak ada dokumentasi arsitektur.

Tiga Jenis Test — Kapan Masing-Masing

◆ Isolated Logic
Unit Test
Test satu class/method dalam isolasi total. Mock semua dependency. Sangat cepat (<1ms per test). Cocok untuk: Service class, helper function, kalkulasi bisnis (harga, diskon, pajak). Bukan untuk controller atau database.
◆ Default Laravel
Feature Test
Test satu HTTP request end-to-end termasuk database. Paling valuable untuk Laravel. Menemukan bug integration yang unit test tidak bisa tangkap. Ini yang harus jadi prioritas utama kamu.
◆ Hati-hati
Integration / E2E Test
Test alur lengkap melibatkan sistem eksternal (payment gateway, email, third-party API). Paling lambat, paling mahal maintenance-nya. Tulis minimal, hanya untuk critical path.

  • Output lebih readable

PHPUnit — Legacy Aman
  • Mature, dokumentasi lengkap

Coverage Tinggi vs Development Speed

⚡ Insight dari Production

100% coverage adalah vanity metric. Coverage 95% yang mencakup happy path + edge case kritis jauh lebih valuable dari 100% coverage yang penuh dengan test trivial.

Aturan praktis: Jika kamu takut refactor karena bisa rusak, itu tanda kamu butuh lebih banyak test, bukan lebih banyak fitur.

Concurrency & Race Condition
Double order, stok minus, duplicate request — solusi praktis

Masalah Nyata yang Sering Diabaikan

⚠ Kasus Nyata
Stok Minus
User A dan B checkout produk yang stok-nya 1 secara bersamaan. Keduanya cek stok = 1 (tersedia). Keduanya create order. Stok jadi -1. Terjadi tanpa ada error.
⚠ Kasus Nyata
Double Charge
User klik tombol bayar dua kali karena loading lambat. Dua request payment dikirim bersamaan. Keduanya sukses. User di-charge dua kali. Ini pernah terjadi di banyak e-commerce.
⚠ Kasus Nyata
Duplicate Record
User registrasi, klik submit lambat, klik lagi. Dua request bersamaan. Keduanya lolos validasi "email belum ada". Dua akun dengan email yang sama terbuat.

Optimistic vs Pessimistic Locking

StrategiCara KerjaKapan PakaiTrade-off
Pessimistic Lock
lockForUpdate()		 Lock row di database saat SELECT. Row tidak bisa di-update proses lain sampai transaction selesai. Stok inventory, saldo akun, semua kasus "baca lalu kurangi". Konflik tinggi. Deadlock risk jika tidak hati-hati. Performa turun saat concurrency sangat tinggi.
Optimistic Lock
version column		 Tidak lock row. Saat update, cek apakah version masih sama. Jika sudah berubah, tolak update. Data yang jarang di-edit bersamaan. Konflik rendah. User profile update. Harus handle retry logic di aplikasi. Kompleksitas di layer aplikasi.
Database Unique Constraint Database enforce keunikan di level storage. Duplicate record prevention. Paling reliable dan simpel. Hanya untuk keunikan data, bukan untuk operasi numeric (stok).
Redis Atomic Lock Distributed lock via Redis. Proses lain tidak bisa jalan sampai lock dilepas. Job deduplication, prevent duplicate payment, critical section yang tidak bisa concurrent. Butuh Redis. Lock bisa orphaned jika proses crash. 
// ✅ Pessimistic lock — stok inventory
DB::transaction(function () use ($productId, $qty) {
    $product = Product::where('id', $productId)->lockForUpdate()->first();

    if ($product->stock < $qty) {
        throw new InsufficientStockException();
    }

    $product->decrement('stock', $qty);
    Order::create([...]);
});

// ✅ Redis atomic lock — prevent double payment
$lock = Cache::lock('payment:user:' . $userId, 30); // 30 detik timeout

if (!$lock->get()) {
    throw new DuplicatePaymentException('Payment sedang diproses');
}

try {
    // proses payment
    $this->paymentGateway->charge($amount);
} finally {
    $lock->release();
}

// ✅ Idempotency key — prevent double request dari frontend
// Frontend kirim unique key per transaksi
Route::post('/payments', function (Request $request) {
    $key = 'idempotency:' . $request->header('Idempotency-Key');
    return Cache::remember($key, 86400, function () use ($request) {
        return $this->processPayment($request);
    });
});
⚡ Decision Rules

Operasi "baca → kurangi/tambah" nilai numerik: Selalu gunakan database transaction + pessimistic lock atau atomic increment/decrement.

Prevent duplicate record: Database unique constraint + catch UniqueConstraintViolationException. Lebih reliable dari application-level check.

Prevent duplicate action dari user (double click, retry): Idempotency key dari frontend + Redis lock di backend.

Jangan implementasi locking jika tidak ada masalah nyata. Premature locking menambah complexity dan deadlock risk.

DTO vs array vs request langsung — kapan DTO wajib

Tiga Pendekatan: Mana yang Tepat?

◆ Anti-pattern
Pass Request Langsung ke Service
$orderService->create($request) — Service jadi tergantung pada HTTP layer. Tidak bisa di-test tanpa HTTP request. Coupling tinggi. Jangan lakukan ini.
◆ Simple & Cepat
Associative Array

◆ Production Standard
DTO (Data Transfer Object)
Typed, immutable, dokumentasi diri sendiri. IDE autocomplete penuh. Refactoring aman. Mudah di-test. Wajib untuk project menengah ke atas.
// ✅ Implementasi DTO di Laravel (PHP 8+ readonly properties)
readonly class CreateOrderData {
    public function __construct(
        public int    $userId,
        public array  $items,        // [{product_id, qty, price}]
        public string $paymentMethod,
        public ?string $notes = null,
        public ?string $couponCode = null,
    ) {}

    // Factory dari Form Request
    public static function fromRequest(StoreOrderRequest $request): self {
        return new self(
            userId:        auth()->id(),
            items:         $request->validated('items'),
            paymentMethod: $request->validated('payment_method'),
            notes:         $request->validated('notes'),
            couponCode:    $request->validated('coupon_code'),
        );
    }
}

// Controller — bersih, tidak ada logic
class OrderController {
    public function store(StoreOrderRequest $request): JsonResponse {
        $data  = CreateOrderData::fromRequest($request);
        $order = $this->orderService->create($data);
        return OrderResource::make($order)->response()->setStatusCode(201);
    }
}

// Service — tidak tahu apa-apa tentang HTTP
class OrderService {
    public function create(CreateOrderData $data): Order {
        // IDE autocomplete penuh, type-safe
        $total = $this->calculateTotal($data->items);
        // ...
    }
}

DTO dan TypeScript Contract

⚡ Sinkronisasi Frontend–Backend

Dengan DTO di backend, kamu punya single source of truth untuk shape data. Ini bisa di-generate otomatis menjadi TypeScript interface menggunakan tools seperti laravel-typescript-transformer (package Spatie).

Artinya: ubah DTO PHP = TypeScript interface di frontend ikut update. Ini mengeliminasi class bug paling umum: frontend dan backend punya asumsi berbeda tentang struktur data.

// PHP DTO otomatis jadi TypeScript via spatie/laravel-typescript-transformer
// PHP:
readonly class CreateOrderData {
    public int $userId;
    public string $paymentMethod;
}

// TypeScript yang di-generate:
interface CreateOrderData {
    userId: number;
    paymentMethod: string;
}
⚠

Jangan buat DTO untuk semua hal. Simple CRUD yang hanya pass data tanpa transformasi tidak butuh DTO. Masukkan DTO saat service mulai punya banyak parameter, atau saat data melewati lebih dari 2 layer.

    return Limit::perMinute(10)->by($request->ip());

// 2. Per User — untuk API endpoint authenticated
RateLimiter::for('api', function (Request $request) {
    return $request->user()
        ? Limit::perMinute(60)->by($request->user()->id)
        : Limit::perMinute(10)->by($request->ip()); // fallback ke IP
});

// 3. Dynamic — limit berbeda per tier user (free vs premium vs enterprise)
RateLimiter::for('api', function (Request $request) {
    $limits = [
        'free'       => 60,
        'premium'    => 300,
        'enterprise' => 1000,
    ];
    $limit = $limits[$request->user()?->plan ?? 'free'];
    return Limit::perMinute($limit)->by($request->user()?->id ?? $request->ip());
});

// 4. Per aksi spesifik — login lebih ketat dari endpoint biasa
RateLimiter::for('login', function (Request $request) {
    return [
        Limit::perMinute(5)->by($request->ip()),                          // per IP
        Limit::perMinute(3)->by($request->input('email') . $request->ip()), // per email+IP
    ];
});

Soft Delete & Data Lifecycle
Kapan soft delete, kapan hard delete, archiving, dampak performa

Soft Delete vs Hard Delete

◆ Gunakan Untuk
Soft Delete
Data yang punya business value setelah "dihapus": user (audit trail), order, invoice, product (history pembelian). Data yang mungkin perlu di-restore. Data yang referenced oleh data lain via foreign key.
◆ Gunakan Untuk
Hard Delete
Session, log entries lama, temporary data, cart yang abandoned. Data yang benar-benar tidak punya value setelah dihapus. Data GDPR yang harus benar-benar dihapus (right to erasure).

Masalah Tersembunyi Soft Delete

⚠

Soft delete bukan silver bullet. Setiap query secara diam-diam menambahkan WHERE deleted_at IS NULL. Tanpa index yang tepat, ini memperlambat semua query di tabel yang besar. Pastikan ada composite index yang include kolom deleted_at.

Multi-Tenant Architecture
Single DB vs Multi DB, kapan perlu, kompleksitas nyata

Apa itu Multi-Tenancy?

Multi-tenant berarti satu aplikasi melayani banyak "tenant" (organisasi/customer), masing-masing dengan data yang terisolasi. Contoh: Aplikasi HR yang dipakai oleh 100 perusahaan berbeda. Setiap perusahaan tidak boleh melihat data perusahaan lain.

Tiga Pendekatan Isolasi Data

◆ Default untuk SaaS
Single DB + tenant_id column
Semua tenant di satu database. Setiap tabel ada kolom tenant_id. Lebih mudah di-maintain, mudah scale, murah. Risk: bug bisa leak data antar tenant jika tidak hati-hati. Cocok untuk 90% SaaS.
◆ Isolasi lebih kuat
Single DB + Schema per Tenant
Satu database, tiap tenant dapat schema/prefix sendiri. Isolasi lebih kuat dari single-tenant. PostgreSQL schema support lebih baik dari MySQL. Middle ground yang bagus.
◆ Enterprise only
Database per Tenant
Tiap tenant dapat database sendiri. Isolasi absolut. Compliance-friendly. Tapi: operasional sangat kompleks, migration harus dijalankan ke semua database, cost tinggi.

Decision: Kapan Butuh Multi-Tenant?

⚡ Pertanyaan Kunci Sebelum Membangun

Pertanyaan 1: Apakah data harus benar-benar terisolasi antar customer? Jika semua customer boleh lihat data yang sama (seperti marketplace publik), ini bukan multi-tenant.

Pertanyaan 2: Berapa banyak tenant yang diantisipasi? Untuk <20 tenant enterprise yang punya budget, pertimbangkan deployment terpisah per tenant — jauh lebih simple.

Pertanyaan 3: Apakah ada compliance requirement (HIPAA, data residency)? Jika ya, database per tenant mungkin diperlukan.

Jangan implementasi multi-tenant sebelum ada kebutuhan nyata. Ini adalah kompleksitas yang significant. Banyak startup sukses mulai dengan single-tenant lalu migrasi setelah terbukti product-market fit.

Zero-Downtime Deployment & Safe Migrations
Expand-Contract pattern, transactional DDL, aturan migrasi yang aman di production

Kenapa Ini Krusial?

Deploy biasa dengan php artisan migrate saat deployment bisa menyebabkan downtime 10–60 detik karena table lock saat ALTER TABLE di tabel besar. Lebih parah: jika kode baru dan kode lama berjalan bersamaan selama rolling deploy, schema yang tidak kompatibel bisa menyebabkan error massal yang sulit di-debug.

Expand-Contract Pattern — Satu-satunya Cara Aman

Phase 1: Expand
→
Phase 2: Migrate Data
→
Phase 3: Contract
PhaseAksiDeploy
1. Expand Tambah kolom/tabel baru tanpa hapus yang lama. Kode baru tulis ke KEDUA kolom (lama & baru). Deploy kode + migrasi additive. Zero risk.
2. Migrate Data Backfill data dari kolom lama ke kolom baru via job/scheduler. Verify integrity. Background process. Tidak butuh deploy.
3. Contract Hapus kolom lama, update kode hanya baca kolom baru. Deploy kode + migrasi destructive. Aman karena data sudah di kolom baru. 
// Contoh: rename kolom 'name' → 'full_name' di tabel users (100jt rows)

// ❌ JANGAN — satu migration sekaligus
Schema::table('users', function (Blueprint $table) {
    $table->renameColumn('name', 'full_name'); // table lock! downtime!
});

// ✅ EXPAND Phase (Deploy 1) — tambah kolom baru, tulis ke keduanya
Schema::table('users', function (Blueprint $table) {
    $table->string('full_name')->nullable()->after('name');
});

// Model: tulis ke KEDUA kolom selama transisi
protected static function booted(): void {
    static::saving(function (User $user) {
        if ($user->isDirty('name')) {
            $user->full_name = $user->name; // sync ke kolom baru
        }
        if ($user->isDirty('full_name')) {
            $user->name = $user->full_name; // backward compat
        }
    });
}

// ✅ BACKFILL Phase — background job, bukan migration!
// app/Jobs/BackfillUserFullName.php
User::whereNull('full_name')
    ->chunkById(1000, function ($users) {
        $users->each(fn($u) => $u->updateQuietly(['full_name' => $u->name]));
    });

// ✅ CONTRACT Phase (Deploy 2) — setelah backfill selesai & verified
Schema::table('users', function (Blueprint $table) {
    $table->dropColumn('name');
});

Point-in-Time Recovery (PITR)

File backup daily tidak cukup jika insiden terjadi pukul 23:50. Kamu kehilangan hampir 24 jam data. PITR memungkinkan restore ke titik waktu yang sangat spesifik.

MetodeRPO (Data Loss)Cara
Daily backup sajaUp to 24 jamRestore file dump, replay manual changes
Daily + WAL archiving (PostgreSQL)Menit ke detikpg_basebackup + continuous WAL streaming ke S3
Managed DB PITR (RDS, Supabase)5 menitKlik restore di console, pilih timestamp

⚡ Aturan Praktis

RPO (Recovery Point Objective) = berapa banyak data boleh hilang. Untuk e-commerce: maksimal 1 jam. Untuk sistem finansial: 5 menit. Untuk blog/CMS: 24 jam mungkin acceptable.

RTO (Recovery Time Objective) = berapa lama sistem boleh down. Tentukan ini sebelum disaster terjadi, bukan sesudah.

Restore drill wajib minimal 1x per kuartal. Banyak tim menemukan backup mereka corrupt atau prosedur restore tidak terdokumentasi hanya saat disaster nyata terjadi.

Gunakan managed database (RDS, Supabase, PlanetScale) jika tim tidak punya DBA. Mereka handle backup, PITR, dan failover otomatis.

Layer 2: Retry dengan Exponential Backoff + Jitter

// Laravel HTTP Client — built-in retry
Http::retry(
    times: 3,
    sleepMilliseconds: function (int $attempt, $exception) {
        // Exponential backoff dengan jitter: 1s, 2s+random, 4s+random
        $baseDelay = (2 ** $attempt) * 1000;
        $jitter     = rand(0, 500); // tambah randomness agar tidak semua request retry bersamaan
        return $baseDelay + $jitter;
    },
    when: function ($exception) {
        // Hanya retry untuk error yang bisa recover
        return $exception instanceof ConnectionException
            || ($exception instanceof RequestException && in_array($exception->response->status(), [429, 502, 503, 504]));
        // JANGAN retry 4xx client error (400, 401, 404, 422) — tidak akan berhasil
    },
    throw: false // jangan throw exception setelah semua retry gagal
)->post('https://api.payment-gateway.com/charge', $payload);

Layer 3: Circuit Breaker

Circuit Breaker mencegah kamu terus memanggil API yang sudah jelas down, menghemat resource dan mempercepat failure response.

// Implementasi Circuit Breaker via Redis
class CircuitBreaker {
    public function __construct(
        private string $service,
        private int    $threshold  = 5,   // gagal 5x → open
        private int    $timeout    = 60,  // 60 detik sebelum coba lagi (half-open)
    ) {}

    public function isOpen(): bool {
        $failures = (int) Cache::get("circuit:{$this->service}:failures", 0);
        $openedAt  = Cache::get("circuit:{$this->service}:opened_at");

        if ($failures >= $this->threshold) {
            if ($openedAt && now()->diffInSeconds($openedAt) < $this->timeout) {
                return true; // circuit masih open, tolak request
            }
            // half-open: coba satu request untuk test
        }
        return false;
    }

    public function recordSuccess(): void {
        Cache::forget("circuit:{$this->service}:failures");
        Cache::forget("circuit:{$this->service}:opened_at");
    }

    public function recordFailure(): void {
        $failures = Cache::increment("circuit:{$this->service}:failures");
        Cache::put("circuit:{$this->service}:failures", $failures, 300);
        if ($failures >= $this->threshold) {
            Cache::put("circuit:{$this->service}:opened_at", now(), 300);
            Log::warning("circuit.opened", ['service' => $this->service, 'failures' => $failures]);
        }
    }
}

// Usage di service
class PaymentService {
    private CircuitBreaker $circuit;

    public function __construct() {
        $this->circuit = new CircuitBreaker('payment-gateway');
    }

    public function charge(array $data): array {
        if ($this->circuit->isOpen()) {
            // Fallback: queue untuk diproses nanti, atau return error yang jelas
            throw new ServiceUnavailableException('Payment gateway sedang tidak tersedia. Coba dalam beberapa menit.');
        }

        try {
            $response = Http::timeout(10)->retry(2, 1000)->post('/charge', $data);
            $this->circuit->recordSuccess();
            return $response->json();
        } catch (Exception $e) {
            $this->circuit->recordFailure();
            throw $e;
        }
    }
}

Timeout eksplisit adalah non-negotiable. Ini adalah hal pertama yang harus ada, bahkan sebelum retry atau circuit breaker.

Jangan retry untuk 4xx errors (400, 401, 403, 404, 422). Request kamu salah — retry tidak akan berhasil dan hanya membuang resource. Retry hanya untuk 5xx, 429, dan connection errors.

// Middleware untuk set HTTP cache headers di Laravel
class CacheResponseMiddleware {
    public function handle(Request $request, Closure $next, string $type = 'default'): Response {
        $response = $next($request);

        // Jangan cache response error atau non-GET
        if (!$request->isMethod('GET') || $response->getStatusCode() >= 400) {
            return $response->header('Cache-Control', 'no-store');
        }

        match ($type) {
            'public'    => $response->header('Cache-Control', 'public, max-age=3600, stale-while-revalidate=300'),
            'private'   => $response->header('Cache-Control', 'private, max-age=300, no-store'),
            'immutable' => $response->header('Cache-Control', 'public, max-age=31536000, immutable'),
            'nocache'   => $response->header('Cache-Control', 'no-cache, no-store'),
            default     => $response->header('Cache-Control', 'no-cache'),
        };

        return $response;
    }
}

ETag — Conditional Request yang Efisien

// ETag: server generate hash dari konten. Browser kirim kembali di If-None-Match.
// Jika sama → 304 Not Modified (tidak ada body, bandwidth hemat 90%)

public function show(Product $product): Response {
    $etag = md5($product->updated_at . $product->id);

    if (request()->header('If-None-Match') === '"' . $etag . '"') {
        return response('', 304); // Not Modified — konten belum berubah
    }

    return response()->json(ProductResource::make($product))
        ->header('ETag', '"' . $etag . '"')
        ->header('Cache-Control', 'public, max-age=60, must-revalidate')
        ->header('Last-Modified', $product->updated_at->toRfc7231String());
}

Cache Stampede Prevention

Cache stampede terjadi saat banyak request datang bersamaan untuk key yang cache-nya baru expired. Semua request langsung hit database secara bersamaan — persis saat load paling tinggi.

// ❌ Rentan stampede
$products = Cache::remember('products.featured', 3600, fn() => Product::featured()->get());

// ✅ Solusi 1: Lock (atomic cache population)
$products = Cache::lock('lock:products.featured', 10)->block(5, function () {
    return Cache::remember('products.featured', 3600, fn() => Product::featured()->get());
});

// ✅ Solusi 2: Probabilistic early expiration (PER)
// Cache "berpeluang" expire lebih awal secara acak, sehingga tidak semua hit database bersamaan
function probabilisticCache(string $key, int $ttl, Closure $callback): mixed {
    $cached = Cache::get($key);
    if ($cached !== null) {
        ['data' => $data, 'expires_at' => $expiresAt] = $cached;
        $beta = 1.0; // tuning parameter
        if (microtime(true) - $beta * log(rand() / getrandmax()) < $expiresAt) {
            return $data;
        }
    }
    $data = $callback();
    Cache::put($key, ['data' => $data, 'expires_at' => microtime(true) + $ttl], $ttl + 10);
    return $data;
}
⚡ Aturan Praktis

Mulai dari HTTP cache headers sebelum Redis. Browser/CDN cache gratis dan tidak butuh infrastruktur tambahan. Jika 40% traffic bisa di-serve dari CDN, beban server turun signifikan.

Jangan set no-store untuk semua endpoint karena "data harus fresh". Gunakan no-cache dengan ETag — data tetap divalidasi tapi tidak perlu re-download jika belum berubah.

Asset frontend harus menggunakan immutable cache. Laravel Mix/Vite sudah menggenerate file hash. Set cache 1 tahun dengan immutable — browser tidak perlu check ulang.

⚠

Hati-hati cache data sensitif di CDN. Jika response mengandung data user spesifik (nama, email, saldo) dan di-cache dengan public, CDN akan serve data user A ke user B. Gunakan private untuk data per-user, dan pastikan ada Vary: Authorization atau Vary: Cookie header.

Octane vs PHP-FPM — Pahami Dulu Perbedaannya

◆ Default & Aman
PHP-FPM
Setiap request = proses PHP baru. Bootstrap ulang dari nol. Memory direset. Tidak ada state yang bocor antar request. Lambat di bootstrap, tapi sangat predictable dan forgiving terhadap bad code.
◆ High Performance
Laravel Octane (Swoole/FrankenPHP)
Aplikasi di-boot sekali, tetap di memory. Setiap request dilayani oleh worker yang sudah siap. 5–10x lebih cepat untuk request ringan. Trade-off: state dari satu request BISA bocor ke request berikutnya.

// Middleware SecurityHeaders — daftarkan di bootstrap/app.php
class SecurityHeadersMiddleware {
    public function handle(Request $request, Closure $next): Response {
        $response = $next($request);

        return $response
            // Cegah browser menebak MIME type (MIME sniffing attack)
            ->header('X-Content-Type-Options', 'nosniff')
            // Cegah iframe embedding (clickjacking)
            ->header('X-Frame-Options', 'SAMEORIGIN')
            // Paksa HTTPS selama 1 tahun, include subdomain
            ->header('Strict-Transport-Security', 'max-age=31536000; includeSubDomains; preload')
            // Kurangi info referrer yang dikirim ke third-party
            ->header('Referrer-Policy', 'strict-origin-when-cross-origin')
            // Izinkan akses fitur browser hanya yang dibutuhkan
            ->header('Permissions-Policy', 'geolocation=(), microphone=(), camera=()')
            // Content Security Policy — sesuaikan dengan kebutuhan
            ->header('Content-Security-Policy',
                "default-src 'self'; " .
                "script-src 'self' https://cdn.jsdelivr.net; " .
                "style-src 'self' 'unsafe-inline' https://fonts.googleapis.com; " .
                "font-src 'self' https://fonts.gstatic.com; " .
                "img-src 'self' data: https:; " .
                "connect-src 'self' https://api.myapp.com; " .
                "frame-ancestors 'none';"
            )
            // Hapus info server
            ->withoutHeader('X-Powered-By')
            ->withoutHeader('Server');
    }
}

protected static function booted(): void {
    static::creating(function (Product $product) {
        $product->slug = static::generateUniqueSlug($product->name);
    });
}

private static function generateUniqueSlug(string $name): string {
    $base = Str::slug($name);
    $slug = $base;
    $i    = 1;
    while (static::where('slug', $slug)->exists()) {
        $slug = "{$base}-{$i}";
        $i++;
    }
    return $slug;
}

RBAC vs ABAC — Kapan Masing-Masing

◆ Cukup untuk kebanyakan kasus
RBAC (Role-Based)
"User dengan role admin bisa hapus apapun." Aturan berbasis peran. Mudah dipahami dan diimplementasikan. Cocok untuk sistem dengan hierarki sederhana. Spatie Permission mengimplementasikan ini.
◆ Untuk logika kompleks
ABAC (Attribute-Based)
"User bisa edit artikel jika dia adalah penulisnya, atau editor, dan artikel belum dipublish, dan bukan dalam periode lock." Aturan berbasis atribut dari user, resource, dan context. Laravel Policy mengimplementasikan ini.

Laravel Policy — ABAC yang Powerful

// php artisan make:policy OrderPolicy --model=Order

class OrderPolicy {
    // Siapa saja yang bisa view order
    public function view(User $user, Order $order): bool {
        return $user->id === $order->user_id          // pemilik
            || $user->hasRole('admin')                // admin
            || $user->hasRole('support');             // CS team
    }

    // Siapa yang bisa update order
    public function update(User $user, Order $order): bool {
        // ABAC: cek user attribute + resource attribute + context
        if ($user->hasRole('admin')) return true;

        // Pemilik hanya bisa edit jika status masih 'pending'
        if ($user->id === $order->user_id && $order->status === 'pending') {
            return true;
        }

        // Support bisa edit order yang di-assign ke mereka
        if ($user->hasRole('support') && $order->assigned_to === $user->id) {
            return true;
        }

        return false;
    }

    // Custom rule kompleks
    public function cancel(User $user, Order $order): Response {
        if ($order->status === 'delivered') {
            return Response::deny('Pesanan yang sudah diterima tidak bisa dibatalkan.');
        }

        if ($order->status === 'shipped' && !$user->hasRole('admin')) {
            return Response::deny('Pesanan yang sudah dikirim hanya bisa dibatalkan oleh admin.');
        }

        if ($user->id !== $order->user_id && !$user->hasRole(['admin', 'support'])) {
            return Response::deny('Anda tidak memiliki akses untuk membatalkan pesanan ini.');
        }

        return Response::allow();
    }
}

// Untuk sistem multi-tenant: pastikan user hanya akses data tenant mereka
// Ini LEBIH dari RBAC — ini adalah data isolation at authorization layer

class BasePolicy {
    // Mixin ini dipanggil sebelum method lain di semua policy
    public function before(User $user, string $ability): ?bool {
        // Super admin bisa akses segalanya
        if ($user->hasRole('super-admin')) return true;

        return null; // lanjut ke method spesifik
    }

    // Helper untuk cek tenant ownership
    protected function belongsToTenant(User $user, Model $model): bool {
        return $model->tenant_id === $user->tenant_id;
    }
}

class OrderPolicy extends BasePolicy {
    public function view(User $user, Order $order): bool {
        // Cek tenant ownership DULU, sebelum cek role
        if (!$this->belongsToTenant($user, $order)) return false;

        return $user->id === $order->user_id || $user->hasRole(['admin', 'support']);
    }
}

// Gate::before untuk global override
Gate::before(function (User $user, string $ability) {
    if ($user->hasRole('super-admin')) return true;

Gunakan Policy untuk semua resource authorization. Policy adalah tempat yang tepat untuk ABAC logic. Controller harus bersih dari if/else authorization.

Jangan percaya pada UI-only authorization. Sembunyikan tombol di Blade, tapi SELALU authorize di controller juga. User bisa langsung hit endpoint API tanpa melalui UI.

Validation vs Sanitization — Beda Fundamental

◆ Tolak yang Salah
Validation
Memastikan data sesuai aturan yang diharapkan. Jika tidak valid → tolak request dengan error message. "Email harus valid", "Harga tidak boleh negatif", "Stok harus integer". Laravel Form Request adalah tempat yang tepat.
◆ Bersihkan yang Masuk
Sanitization
Membersihkan data tanpa menolaknya. Strip HTML tags, trim whitespace, normalize encoding. Dilakukan SETELAH validation berhasil. Tujuan: keamanan dan konsistensi, bukan correctness checking.

class OrderService {
    public function create(CreateOrderData $data): Order {
        // Business rules — tidak bisa dilakukan di Form Request
        $this->validateProductsAvailability($data->items);
        $this->validateCouponApplicability($data->couponCode, $data->userId);
        $this->validateOrderLimits($data->userId);

        return DB::transaction(fn() => $this->processOrder($data));
    }

    private function validateProductsAvailability(array $items): void {
        foreach ($items as $item) {
            $product = Product::lockForUpdate()->find($item['product_id']);
            if ($product->stock < $item['qty']) {
                throw new InsufficientStockException(
                    "Stok {$product->name} tidak cukup. Tersedia: {$product->stock}"
                );
            }
            if (!$product->active) {
                throw new ProductUnavailableException("{$product->name} sudah tidak tersedia.");
            }
        }
    }
}

// React Error Boundary — tangkap rendering error sebelum crash seluruh halaman
class ErrorBoundary extends React.Component<{children: React.ReactNode}, {hasError: boolean, error?: Error}> {
    state = { hasError: false };

    static getDerivedStateFromError(error: Error) {
        return { hasError: true, error };
    }

    componentDidCatch(error: Error, info: React.ErrorInfo) {
        // Kirim ke Sentry
        Sentry.captureException(error, { extra: info });
    }

    render() {
        if (this.state.hasError) {
            return (
                <div className="flex flex-col items-center py-16 text-center">
                    <p className="text-lg font-semibold">Terjadi kesalahan</p>
                    <p className="text-gray-500 mt-2">Tim kami sudah diberitahu. Coba muat ulang halaman.</p>
                    <button onClick={() => window.location.reload()} className="mt-4 btn-primary">
                        Muat Ulang
                    </button>
                </div>
            );
        }
        return this.props.children;
    }
}

class ProcessPaymentJob implements ShouldQueue {
    use Dispatchable, InteractsWithQueue, Queueable, SerializesModels;

    public int   $tries    = 3;     // retry 3 kali
    public int   $timeout  = 60;    // kill jika > 60 detik
    public int   $backoff  = 30;    // tunggu 30 detik sebelum retry
    public bool  $deleteWhenMissingModels = true; // jangan gagal jika model sudah dihapus

    public function __construct(private readonly int $paymentId) {}

    public function handle(PaymentService $service): void {
        $payment = Payment::findOrFail($this->paymentId);

        // Idempotency check — jangan proses dua kali
        if ($payment->status !== 'pending') {
            Log::info("payment.skip_duplicate", ['payment_id' => $this->paymentId]);
            return;
        }

        $service->process($payment);
    }

    // Dipanggil setelah semua retry gagal
    public function failed(Throwable $exception): void {
        Log::error('payment.job_failed', [
            'payment_id' => $this->paymentId,
            'error'      => $exception->getMessage(),
        ]);

        Payment::find($this->paymentId)?->update(['status' => 'failed']);

        // Alert ops team
        Notification::route('slack', config('services.slack.ops_webhook'))
            ->notify(new PaymentJobFailed($this->paymentId, $exception));
    }

    // Backoff yang meningkat — exponential
    public function backoff(): array {
        return [30, 60, 120]; // 30s, 1 menit, 2 menit antar retry
    }
}

⚡ Tanda-tanda Saatnya Scale

CPU server konsisten > 70%: Butuh lebih banyak server atau optimasi kode.

Database connection pool habis: Butuh read replica atau connection pooler (PgBouncer untuk PostgreSQL).

Queue depth terus bertambah: Butuh lebih banyak queue workers.

Response time P95 > 2 detik: Investigasi bottleneck sebelum scale — mungkin ini adalah masalah query, bukan kapasitas server.

Jangan scale prematur. Satu server yang dioptimasi dengan baik bisa handle traffic yang sangat besar. Premature scaling menambah kompleksitas operasional tanpa benefit nyata.

Dependency Injection Deep Dive
Laravel IoC Container, binding, interface, testability, anti-patterns

Kenapa DI Lebih dari Sekedar Syntax Sugar

Dependency Injection bukan tentang bagaimana cara inject class ke constructor. Ini tentang inversion of control — class tidak membuat dependency-nya sendiri, dia menerima dari luar. Dampaknya: testability jauh lebih mudah karena kamu bisa swap dependency dengan mock di testing.

DI yang Benar vs Anti-Pattern

// ❌ Anti-pattern: hardcoded dependency
class OrderService {
    public function create(array $data): Order {
        $mailer = new SmtpMailer(); // hardcoded — tidak bisa di-mock saat testing!
        $sms    = new TwilioSms();  // hardcoded — memanggil API real saat test!
        $mailer->send($data['email'], 'Order Confirmation', '...');
    }
}

// ✅ Dependency Injection — testable dan swappable
class OrderService {
    public function __construct(
        private MailerInterface $mailer,  // interface, bukan konkret class
        private SmsInterface    $sms,
    ) {}

    public function create(array $data): Order {
        $this->mailer->send($data['email'], 'Order Confirmation', '...');
    }
}

// Interface
interface MailerInterface {
    public function send(string $to, string $subject, string $body): void;
}

// Implementasi nyata
class SmtpMailer implements MailerInterface {
    public function send(string $to, string $subject, string $body): void {
        Mail::to($to)->send(new OrderConfirmationMail($subject, $body));
    }
}

// Implementasi untuk testing
class FakeMailer implements MailerInterface {
    public array $sent = [];
    public function send(string $to, string $subject, string $body): void {
        $this->sent[] = compact('to', 'subject', 'body');
    }
}

// Binding di ServiceProvider
class AppServiceProvider extends ServiceProvider {
    public function register(): void {
        // Bind interface ke implementasi konkret
        $this->app->bind(MailerInterface::class, SmtpMailer::class);
        $this->app->bind(SmsInterface::class, TwilioSms::class);

        // Context-based binding: PaymentService pakai StripeMailer, bukan SmtpMailer
        $this->app->when(PaymentService::class)
            ->needs(MailerInterface::class)
            ->give(StripeMailer::class);
    }
}

// Testing — swap dependency dengan fake
it('sends confirmation email after order created', function () {
    $fakeMailer = new FakeMailer();
    app()->bind(MailerInterface::class, fn() => $fakeMailer);

    $service = app(OrderService::class); // auto-inject FakeMailer
    $service->create(['email' => 'user@test.com', ...]);

    expect($fakeMailer->sent)->toHaveCount(1);
    expect($fakeMailer->sent[0]['to'])->toBe('user@test.com');
});

Binding Patterns di Laravel

// 1. bind() — baru instance setiap kali dipanggil
$this->app->bind(ReportGenerator::class, PdfReportGenerator::class);

// 2. singleton() — satu instance sepanjang request lifecycle
$this->app->singleton(CurrencyService::class, function ($app) {
    return new CurrencyService(config('services.currency.api_key'));
});

// 3. instance() — bind object yang sudah dibuat
$this->app->instance('config.cache', $configArray);

// 4. scoped() — singleton per request (cocok untuk Octane)
$this->app->scoped(CurrentTenant::class, function () {
    return Tenant::find(request()->header('X-Tenant-ID'));
});

// 5. Conditional binding berdasarkan environment
if ($this->app->environment('testing')) {
    $this->app->bind(PaymentGateway::class, FakePaymentGateway::class);
} else {
    $this->app->bind(PaymentGateway::class, StripeGateway::class);
}
⚡ Aturan Praktis

Selalu inject interface, bukan concrete class untuk dependency yang mungkin berubah atau perlu di-mock di test (email, SMS, payment, external API).

Jangan over-engineer DI untuk dependency yang tidak akan berubah. Inject OrderRepository boleh sebagai concrete class jika kamu yakin tidak akan ganti implementasi. Interface wajib untuk third-party integration.

Laravel Facades adalah syntactic sugar, bukan anti-pattern. Mail::send() internally menggunakan IoC container. Tapi untuk testability yang lebih jelas di unit test, prefer constructor injection.
